# 04 · 路线图

> 五个里程碑，每个都有明确的验收标准。原则：每个阶段结束时，产品都比上一阶段「多闭环一段」。

## 总览

| 里程碑 | 主题 | 一句话目标 |
| --- | --- | --- |
| M0 | 奠基 | 定义清楚做什么，验证最小技术路径 |
| M1 | MVP | 一个对话框做出能玩的小游戏 |
| M2 | 团队 | 七角色 Agent 团队真正协作起来 |
| M3 | 双端 | 手机 & 桌面 APP 上架 |
| M4 | 闭环 | 从想法到上线全程在 Waypoint 内完成 |

## M0 · 奠基

- **目标**：完成产品与技术定义，跑通「LLM 生成可运行 HTML5 游戏」的最小验证。
- **范围**：
  - 产品 / 架构 / Agent 设计文档（本 docs 目录）
  - 交互原型（对话流 + 预览 + 看板的低保真）
  - 技术 Spike：单次对话 → 生成可玩 HTML5 小游戏 demo
- **验收标准**：✅ 用纯对话生成至少 1 个可玩的 HTML5 小游戏（如贪吃蛇 / 接元宝），在浏览器中运行通过
- **不做**：多 Agent、账号体系、发布

## M1 · MVP（单 Agent）

- **目标**：Web 端 MVP——一个「全能执行者」Agent 模拟整条流水线，用户从 0 得到可玩游戏。
- **范围**：
  - Web 对话界面 + 实时预览
  - 玩法模版框架第一版（2-3 个品类：放置 / 文字冒险 / 休闲）
  - 模板库 ≥5 个，一键起项目
  - 迭代循环：试玩 → 反馈 → 修改 → 再预览；版本可回滚
- **验收标准**：✅ 普通用户（非程序员）10 分钟内从一句话想法得到可玩的小游戏，并能完成 ≥3 轮迭代
- **不做**：角色拆分、发布、手机端

## M2 · 团队（多 Agent）

- **目标**：把全能执行者拆成七个角色，用户能看到并指挥一支团队。
- **范围**：
  - 制作人为中心的编排器；任务状态机与看板
  - Agent 工作直播（过程透明）；进展日报
  - 用户决策点交互（立项确认 / 玩法二选一 / 美术三选一）
  - 共享项目记忆第一版（立项书 / 决策日志 / 资产索引）
  - 自动化测试门禁
- **验收标准**：✅ 用户的一个需求被自动拆解为 ≥3 个角色的协作任务并交付；✅ 关键决策均由用户拍板
- **不做**：真机 APP、对外发布

## M3 · 双端 APP

- **目标**：手机 & 桌面对话 APP 可用、可上架，项目云端同步。
- **范围**：
  - 桌面 APP（Tauri ⏳）与手机 APP（Flutter ⏳），体验对齐 Web 端
  - 账号体系、项目云同步、双端无缝接力
  - 推送：进展日报、待决策提醒
- **验收标准**：✅ 同一项目在手机与桌面间接力推进无断裂；✅ 双端通过内部质量验收并提交商店审核
- **不做**：游戏对外发布渠道

## M4 · 闭环（上线）

- **目标**：作品的构建、发布、运营全程在 Waypoint 内完成——「直接可以上线」兑现。
- **范围**：
  - 一键发布：构建流水线 → Web/H5 链接（分享即玩）；发布评审门禁
  - 运营格局接入：首周数据报告、迭代建议回流 Backlog
  - 遥测看板（留存 / 流失点）对用户可视化
- **验收标准**：✅ 一个用户作品从想法到公网可玩全程未离开 Waypoint；✅ 运营建议驱动至少一轮上线后迭代
- **远期**：原生壳打包上架、多人玩法、商业化（订阅 / 额度）

## 风险与前置依赖

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 生成质量不达「可玩」底线 | M1 不成立 | M0 Spike 提前验证；玩法框架收窄自由度 |
| 多 Agent 成本失控 | M2 不可持续 | 模型路由分级 + 预算护栏（见 03-architecture） |
| 双端体验不一致 | M3 延期 | 应用层协议先行，客户端薄壳化 |
| 发布合规（内容审核） | M4 受阻 | 内容安全从 M1 起内建，不留到最后 |
